01 — System Overview

Architecture Diagram

The SPA runs entirely in the browser. Every operation hits a Flask REST API at /api/* over HTTP. There is no server-side rendering — the backend is pure JSON.

02 — Layer Breakdown

System Layers

Each layer has a single responsibility. The SPA never touches the database directly.

🖥️
Vue 3 SPA
FRONTEND — PORT 5173 (dev)
Built with Vite 8. Vue Router guards redirect unauthenticated users to /login. Pinia stores hold all app state. ECharts renders dashboard charts. TanStack Table powers the sortable project table.
🔌
api/index.js
HTTP CLIENT — fetch() WRAPPER
Single module that wraps all fetch() calls. Reads JWT from localStorage, injects it as Authorization: Bearer ... on every request, normalises error envelopes, and auto-redirects to /login on 401.
⚗️
Flask REST API
BACKEND — PORT 5000
App factory wires JWT, CORS, rate limiter, and all blueprints. Every response is a JSON envelope. All errors follow {error:{type,message}}. Blueprints: auth, projects, tasks, comments, records, stats, sheets, users.
🔐
JWT Auth
FLASK-JWT-EXTENDED — 12h EXPIRY
Login returns a signed JWT. The identity is the stringified user.id; role + name travel as additional claims. No refresh tokens — 12 h expiry is the trade-off. Rate-limited: 10 logins / min / IP.
🗄️
SQLAlchemy ORM
DB-PORTABLE — SQLite / PG / MSSQL
All models use only portable column types (no DB-specific syntax). Schema auto-creates on startup via Base.metadata.create_all(). The session is scoped and released at teardown via Session.remove().
📊
Stats Engine
SQL GROUP BY — NO PYTHON LOOPS
All dashboard aggregations (funnel counts, fiscal bars, domain donut, upcoming) use SQL GROUP BY + func.count/sum. Zero full-table Python loops — single round-trip to DB for all KPIs.

06 — Getting Started

Installation Guide

Choose your platform. The app runs on Windows (Waitress) and Linux (Gunicorn).

  • 01
    Clone the repository
    Get the source code onto your machine.
    git clone https://github.com/your-org/project-tracking.git cd project-tracking
  • 02
    Create Python virtual environment (Backend)
    Python 3.11 recommended. Always use .venv — the global env has conflicting packages.
    cd backend py -3.11 -m venv .venv .venv\Scripts\pip install -r requirements-dev.txt
  • 03
    Configure environment variables
    Copy .env.example to .env and set your secrets and DB URL.
    # Database — default falls back to SQLite if not set DATABASE_URL=postgresql+psycopg2://postgres:P%40ssw0rd@localhost:5432/ProjectTracking # Secrets — CHANGE IN PRODUCTION! SECRET_KEY=your-super-secret-key-here JWT_SECRET_KEY=your-jwt-secret-here JWT_HOURS=12 # CORS: * for dev, restrict in production CORS_ORIGINS=* # Seed demo data on first start (optional) SEED_ON_START=true
  • 04
    Start the Flask backend
    Schema auto-creates on startup. Visit http://localhost:5000/api/health to verify.
    # Development mode .venv\Scripts\python -m flask run --port 5000 # OR seed demo data first .venv\Scripts\python seed.py
  • 05
    Install and start the frontend
    Vite dev server proxies API calls to Flask. Hot-reloads on save.
    npm install npm run dev # → http://localhost:5173
  • 06
    Run tests
    25 tests across auth, projects, tasks, comments, stats, and records. Always run inside .venv.
    .venv\Scripts\python -m pytest tests/ -v # 25 tests — uses in-memory SQLite (TestConfig)
  • 01
    Clone and set up backend
    git clone https://github.com/your-org/project-tracking.git && cd project-tracking/backend python3.11 -m venv .venv source .venv/bin/activate pip install -r requirements-dev.txt
  • 02
    Configure and seed
    cp .env.example .env # Edit .env with your DB URL and secrets python seed.py # loads demo data
  • 03
    Run backend + frontend
    # Terminal 1 — backend flask run --port 5000 # Terminal 2 — frontend cd ../frontend && npm install && npm run dev
⚠ NOTE: No official Dockerfile is included in the repo. The setup below is a recommended pattern based on the existing requirements.txt and Vite config.

07 — Production

Deployment Guide

Two deployment targets: Windows Service (Waitress) for on-prem, and Linux server (Gunicorn + Nginx).

🪟 Windows — Waitress WSGI Service
# backend/wsgi.py from app import create_app app = create_app()
# Install as Windows service via NSSM or run directly: .venv\Scripts\waitress-serve \ --port=5000 \ --call wsgi:app # Or use the included batch file: start_service.bat
  • Set FLASK_DEBUG=false in .env
  • Set strong SECRET_KEY & JWT_SECRET_KEY
  • Set CORS_ORIGINS=https://yourapp.com
  • Use PostgreSQL — not SQLite for production
  • Run npm run build → serve frontend/dist/ via IIS or Nginx
🐧 Linux — Gunicorn + Nginx
# Add to requirements.txt: gunicorn>=22.0 gunicorn --workers 4 --bind 0.0.0.0:5000 wsgi:app
server { listen 80; root /var/www/dist; # frontend/dist index index.html; # SPA fallback location / { try_files $uri $uri/ /index.html; } # Proxy API to Gunicorn location /api/ { proxy_pass http://127.0.0.1:5000; proxy_set_header Host $host; } }
💡 Tip: With Nginx reverse-proxying, set CORS_ORIGINS="" (same-origin). No need for CORS headers when frontend and backend share the same domain.
🔒 Production Security Checklist
  • ☐ Change SECRET_KEY and JWT_SECRET_KEY — never use defaults
  • ☐ Set FLASK_DEBUG=false — never expose debug mode
  • ☐ Set CORS_ORIGINS to exact domain(s) only
  • ☐ Use PostgreSQL — SQLite not suitable for concurrent writes
  • ☐ Set SEED_ON_START=false — it DROPS all tables first
  • ☐ Rate-limit via Nginx/WAF in addition to Flask-Limiter
  • ☐ Configure Redis for rate-limit storage (RATELIMIT_STORAGE_URI)
  • ☐ Enable HTTPS — JWT in localStorage is XSS-accessible
  • ☐ Restrict DB user to only the app database
📦 Build the Frontend
# Create production bundle npm run build # Output: frontend/dist/ (static files) ✓ index.html (SPA shell) ✓ assets/ (hashed JS + CSS chunks) # Serve dist/ with any static server: # - Nginx root directive # - IIS static content # - Apache DocumentRoot # - GitHub Pages (no /api/ proxy needed externally)
⚠ SPA Routing: The Vite build outputs a single index.html. All routes (/kanban, /table, etc.) are client-side. Your web server must return index.html for all non-/api/ paths — configure a fallback rule.

08 — Developer Guide

Development Workflows

Key patterns, pitfalls, and conventions every contributor should know.

⚡
Hot Reload Dev Loop
VITE + FLASK
Run Flask on :5000 and Vite on :5173 simultaneously. The Vite dev server proxies /api/* requests to Flask (configure vite.config.js proxy if needed) or use CORS_ORIGINS=* in .env for cross-origin requests.
🏗️
Adding a New API Route
BLUEPRINT PATTERN
Create a new blueprint in app/api/yourmodule.py, register it in app/api/__init__.py, add tests in tests/test_yourmodule.py. Use @jwt_required() for protected routes and require_owner_or_admin() for authz.
🧪
Running Tests
PYTEST — 25 TESTS
Always use .venv\Scripts\python -m pytest — the global Python env has a hydra package that breaks pytest plugin loading. Tests use TestConfig with in-memory SQLite. Auth fixture password: secret123.
🎨
Frontend Conventions
VUE 3 + PINIA
Single typeface: IBM Plex Sans Thai via var(--font). Never add new font families. Monospace labels use .mono class with font-variant-numeric: tabular-nums. All API calls go through api/index.js — never use fetch() directly in components.
📌
Authorization Model
OWNER OR ADMIN
Admin: full access to all resources. Member: can only edit/delete own projects, tasks, and comments. Enforced by require_owner_or_admin(user, owner_id) in app/api/helpers.py. First registered user auto-promoted to admin.
⚠️
Common Pitfalls
READ BEFORE DEBUGGING
• ptrack.checked maps to DB column named "check" — never raw SQL.
• ptemplate has no process column — resolved at read via process_tags join.
• Rate limit 429 on login — 10/min/IP, wait or restart Flask.
• Tag names >48 chars raise 422 before DB.
• Owner check uses pm field owner_id, not always admin.
